# CHAT-MEDIA-01 — private incoming image/PDF attachments

29October2026 Root execution design under the human-approved CHAT plan/DEC187, CH023/028/054/055/056. LINE Login configuration remains explicitly deferred by the human. Preserve anonymous Student identity, Dashboard-only Staff chat, verified raw-body webhooks and the existing browser ChatAttachment DTO. OpenCode owns its current frontend worktree; Root changes no delegated UI files.

## Decision and scope

Use the existing Supabase private Storage + encrypted metadata + PostgreSQL lease queue, with a dedicated Node MEDIA worker so file downloads do not block Student/Staff inbox fairness. DB bytea would bloat the application DB and transactions; a new S3/Redis service adds infrastructure without a requirement. A separate chat bucket/purpose avoids sharing knowledge publication/original-artifact authority.

This slice receives Student IMAGE and FILE(PDF) messages and exposes authorized Staff download links through the existing Inbox attachment slot. It does not infer image/PDF contents, add vision/model calls or public URLs. Unsupported kinds retain the prior SYSTEM presentation guard. Private outbound files remain a separate next slice: an expiring bearer link alone cannot prove the browser is the intended LINE recipient; do not silently treat it as recipient authentication or add a Student profile.

Current official sources checked29October: [LINE receive/get-content](https://developers.line.biz/en/docs/messaging-api/receiving-messages/#get-user-sent-content-with-webhook), [Messaging API](https://developers.line.biz/en/reference/messaging-api/#get-content), [Supabase access control](https://supabase.com/docs/guides/storage/security/access-control). LINE content is fetched by message ID at api-data.line.me, authenticated with Student channel token; content can expire. Do not fetch event-supplied external URLs or assume retention duration. No actual LINE content calls are needed for controlled verification.

## Data and invariants

Add private.chat_attachments (one per USER message): UUID id, unique message_id FK, source_event_id FK, immutable encrypted source metadata, original kind, PENDING/PROCESSING/READY/FAILED, attempts<=3/next_retry_at/lease token+expiry, confirmed MIME/bytes/SHA256/object UUID, timestamps and fixed error code. Private RLS, no browser grants/policies; index every FK/claim path. Browser projects id/name/MIME/size/status/downloadUrl only. Unknown size is0; unavailable/PENDING/FAILED downloadUrl is null. The raw original filename remains in the encrypted source webhook; normalized display filename is separately encrypted and never determines MIME, authorization or object path.

Register inside existing durable verified message processing, after the actual USER message insert. Re-read encrypted source event to recover bounded file metadata without widening the shared LINE event contract. Validate source channel/message id/type/Student identity against the current message/session. Replay cannot register a second job. Malformed metadata is an explicit FAILED record or safe fallback label, never a silently dropped message. Existing raw HMAC-before-JSON and encrypted original event remain.

Claim one eligible/expired PROCESSING row using FOR UPDATE SKIP LOCKED; issue a fresh UUID lease, max3 attempts,90second lease. Network fetch/upload occurs only after commit/release. Fixed byte cap10MiB, timeout15seconds per external operation; inspect signature and declared MIME, decode JPEG/PNG with Sharp limited to16M pixels/10 seconds, and structurally inspect PDF in an isolated bounded child (10 seconds, 256MiB JS heap, at most1000 pages). Encrypted or invalid PDFs fail. These checks are not malware scanning or vision. Fetch only the canonical LINE content URL; reject redirects, bad status, unknown encoding, oversized declared/streamed body and empty/mismatched content. 404/expired/invalid/unsupported are terminal; transient errors use bounded exponential backoff. A worker crash after final attempt must become FAILED, not a stuck PROCESSING row.

For a verified Student unsend event, record a private purpose-keyed hash tombstone and revoke matching attachments without creating a Student session. This covers unsend arriving before the original event. Pending leases are cancelled; previously READY objects remain private but cannot be displayed or downloaded, and status changes invalidate Inbox. This slice handles file access on unsend; it does not claim text-unsend handling. Bytes already delivered cannot be recalled.

Use private bucket chat-attachments, application-encrypted binary envelopes with HKDF purpose chat-attachment:v1/AES256GCM. AAD binds attachment/message/source-event/object UUID, MIME, exact size and SHA. Path is attachmentId/leaseToken.yruc; no filename/LINE identity in the path. Each attempt uses its own object so an expired worker cannot overwrite a later winner. Upload is no-upsert; uncertain uploads may leave at most the bounded attempt objects private. No automatic original/history deletion or unproven cleanup claim. Explicit provision inspects existing bucket settings and never rewrites them; actual setup happens through a guarded development action after owned tests.

Finalize READY only under the same live lease and fresh source ownership checks. Persist the exact winning object/ref; late leases cannot publish metadata. Permanent failure remains visible; source messages survive. Trigger existing per-Staff private invalidation when status changes for an assigned ticket; pending unassigned messages obtain current attachment state when routed/read. Broadcast contains invalidation only, no file names/content.

## Staff read boundary

GET /api/chat/tickets/[ticketId]/attachments/[attachmentId] uses existing verified Staff subject, active profile/department/sensitivity and current message/ticket/conversation ownership. Buffer at most10MiB+envelope overhead outside SQL, decrypt and verify exact reference/SHA, then recheck current authorization/source/reference before constructing the response. No DB connection/transaction spans storage HTTP. Deny wrong-case/nonexistent/revoked scope without bytes; late revocation after the final authorization boundary cannot recall bytes already in flight.

Use private,no-store/nosniff, safe encoded Content-Disposition attachment, restrictive CSP and no public storage redirects. Serve PDF as a download, not unsandboxed active content on the app origin. Preserve complete file bytes; no silent truncation. Range/HEAD/unrecognized query are not used to bypass the same permission boundary. Existing readThread adds attachments for only its selected message window without N+1 queries and without changing DTO shape.

## Next slice: outbound files and recipient identity (planned, not implemented)

CHAT-MEDIA-02 / CH023/028/054/055/056: Staff uploads a bounded, validated image/PDF to private encrypted storage as a case-bound draft. The existing assigned/supervisor authorization and current ticket status must be checked before accepting, confirming and dispatching. Upload, validation and Storage HTTP stay outside SQL transactions; unique request IDs and lease-owned immutable object paths prevent retry duplication and stale completion. An explicit reviewed recipient is obtained from the current ticket/conversation and private LINE identity, never a client-provided Student ID. If upload, LINE delivery or permission changes fail, preserve an honest retryable state without claiming delivery or sending to another case. Uploaded but abandoned objects need a separately audited retention policy; do not invent automatic deletion.

For a private Student file link, use a Student LIFF application and LINE Login channel under the same LINE Provider as the Student Messaging channel. [LINE's current guidance](https://developers.line.biz/en/docs/liff/using-user-profile/) requires the browser to pass a raw ID token to the server, which verifies it with LINE and the expected channel ID; the browser-provided user ID or decoded token is not authentication. The verified subject maps through the existing purpose-keyed LINE identity hash to the case recipient, without a Student profile database. A link or token by itself does not grant access to another recipient's file. Validate audience, issuer and expiration; do not log tokens or profile data. Use HTTPS, bounded requests and fail closed when verification is unavailable. Staff and Student Login channels may require distinct provider configuration; configuration and actual OAuth acceptance remain human-deferred.

After verification, issue only a short-lived, scoped, HttpOnly/Secure/SameSite session or require verified token on guarded byte requests. Bind authorization to the specific active attachment/case/recipient, recheck after Storage retrieval, deny cross-user access, handle revoked/expired sessions and prevent cache/referrer leakage. Display a clear safe download action rather than an unguarded public PDF URL. LINE supports image message types with URLs but a public URL cannot be treated as an authenticated private attachment; use a recipient-checked viewer when confidentiality is required.

Implementation dependencies: (1) freeze outbound message/draft/lease and recipient-proof contracts; (2) build verified Student identity and scoped viewer/session; (3) extend private storage and Staff upload with atomic outbox integration; (4) connect delegated Inbox composer without overwriting concurrent OpenCode UI work; (5) verify same-user/cross-user, wrong provider, expiry, stale lease, concurrent assignment/revoke, retry/duplicate, reconnect, and partial delivery using controlled credentials; (6) defer actual LINE channel setup and end-to-end manual acceptance until the human is ready. Existing inbound-only metadata assumes a Student webhook source; do not reuse its constraints for Staff uploads without an additive, reviewed schema design.

### CHAT-MEDIA-02A — verified Student LINE subject prerequisite

CH023/028/054/055/056; Root owns `lib/chat/student-line-verification.ts` and `tests/student-line-verification.test.ts`. Before any viewer API or token/session feature, build a server-only, disabled-by-default verification adapter. It posts the raw bounded LIFF ID token and server-configured channel ID to the exact official LINE verification endpoint, using a bounded timeout, no redirects, bounded response and no token/profile logging; only a successfully verified issuer, audience, expiry and subject is eligible for the existing anonymous Student identity HMAC. A client-decoded subject or arbitrary URL is never accepted as proof. Return only the HMAC and expiry; distinguish invalid credentials from an unavailable provider without exposing upstream body. Configuration and the same-Provider relationship are prerequisites to later actual viewer use; no Student profile, cookie, grant or exposed endpoint is created by this prerequisite.

The configured adapter takes channel ID and encryption key only from server configuration, and stays unavailable until both `LINE_STUDENT_MEDIA_VIEWER_ENABLED=true` and `LINE_STUDENT_LOGIN_SAME_PROVIDER_CONFIRMED=true` are explicitly configured together with `LINE_STUDENT_LOGIN_CHANNEL_ID`. These are design-gated server settings, not evidence the Student Login channel or feature is currently available. Next.js `server-only` prevents accidental Client Component use; the underlying verifier is private and cannot be called to bypass the configuration gate.

Acceptance: test server-issued expected subject mapping; wrong channel/issuer/expiry/subject; malformed/oversized token and response; timeouts, ignored abort, redirects and provider errors; non-disclosure of raw token/identity/profile. Tests use controlled adapters only, not real LINE. This subtask cannot by itself unlock file delivery or mark CHAT-MEDIA-02 complete.

### CHAT-MEDIA-02B — attachment-scoped Student identity envelope prerequisite

Root owns `lib/chat/student-media-session.ts` and `tests/student-media-session.test.ts`. Following successful server-side LINE token verification, a future viewer may create an encrypted/authenticated session scoped to exactly one attachment ID and the verified anonymous identity hash. Use purpose-separated AES-256-GCM, a fresh random nonce and a lifetime bounded by both five minutes and the verified LINE token expiry. Deny malformed or altered envelopes, wrong attachment, expiry and future-issued sessions. Return no LINE subject or token to the browser; future API integration must set a Secure/HttpOnly/SameSite cookie and recheck current attachment, ticket and recipient authority before and after storage access. This envelope proves only short-lived identity for a single attachment; it does not itself authorize any file or provide immediate LINE account revocation. No public route or cookie is enabled in this prerequisite. Controlled tests prove tamper/wrong attachment/expiry/key isolation; no real LINE call.

### CHAT-MEDIA-02C — outbound draft and recipient fence (next design work)

The next additive private schema must be separate from the inbound table: incoming attachments require an immutable Student webhook event and USER message, whereas a Staff file has neither. Store the owning Staff, case/conversation, current Student session and hashed recipient, case revision and assignment epoch, request ID/content digest, immutable object ref and explicit draft/upload/delivery state. Source recipient data only from the current ticket and `private.line_identities`, and authenticate the recipient hash again both before and after Storage reads. A cross-case request or changed subject/revision/assignment must not retarget a draft. Unique request receipts and live lease checks must make concurrent and repeated uploads deterministic; full object bytes are written outside SQL, under a per-attempt immutable path. Do not attach a file to a Student-visible message before upload is verified and Staff explicitly confirms the exact recipient.

At confirm, use existing `STAFF_REPLY` conversation/state rules and delivery guard/cases in the same transaction as attachment-message/outbox association. The existing LINE message schema accepts text, so send a fixed LIFF viewer link as text, never a public direct object URL. Student byte access is permitted only for a message confirmed as delivered (`SENT`), after current verified identity and attachment/case binding checks. A delivered file may remain available after a case closes while still respecting explicit revocation and retention policy; a queued, failed, suppressed or uncertain delivery cannot be represented as delivered. LINE or Storage failure must not discard the Staff draft or announce success. Existing history, receipts, revisions, active permissions and idempotency fences remain authoritative. Viewer endpoint paths, exact DTOs, cleanup lifecycle and live production capacity must be frozen and tested before this design becomes a migration or public API.
