- Keep one assignee per ticket. Existing `applyTicketAction(ACCEPT)` locks conversation/ticket, checks revision and rejects an assigned ticket. LINE actions reuse this boundary and add durable event-idempotent success/already-taken feedback. A delivered button is never authority; do not promise that old buttons disappear from every chat.
- Explicit case-open selects one active case for that bound staff member. An accept receipt offers “เปิดคุยเคสนี้”; accepting another case never switches an existing reply target. New alerts never switch it either. Show the case code and “งานของฉัน”, “เปลี่ยนเคส”, “หยุดคุย”. Text relays only to the explicitly selected, currently assigned, active HUMAN case. Missing/expired selection asks for selection; never choose the latest case. Proposed lifetime is 30 minutes from selection without silent renewal, an engineering choice rather than source wording.
- Start with text in one-to-one Staff OA chats. Reuse ticket-service `STAFF_REPLY`, Student outbox, sender/history and idempotency. Regular STAFF replies only to own cases; supervisory intervention stays explicit and scoped. Incident visibility never grants assignment.
- GENERAL USER messages may reach the current assigned staff member. SENSITIVE/RESTRICTED details remain in Dashboard; LINE gets generic notices. No USER text or technical identity goes to all departmental staff. Recheck binding, active actor, scope, privacy, assignment and lifecycle before queueing and protected dispatch. Reassign/close/unlink/revoke invalidates selection and pending content. Started HTTP and mutation must share a delivery fence.
- LINE application opening is not a documented Messaging API webhook event. API acceptance, deliberate case-open and reply status are separate observations. Record a per-staff read cursor only after a deliberate case-open/read action, never after API200, accept, preview or digest generation. It covers the displayed snapshot; concurrent newer messages remain new.
- Fresh “งานของฉัน” reads assigned cases/pending USER messages; “คิวฝ่าย” reads eligible unassigned work. Provide the fixed typed commands as well as buttons so recovery does not depend on a still-visible QuickReply or optional Rich Menu setup. Lists remain usable after old tokens expire. Show cases, distinct anonymous sessions and assigned staff separately; sessions are not verified people. Historical notification text is a snapshot, never current queue authority. A requested digest can summarize backlog; merely opening LINE must not be claimed to trigger it.

Official checks: [LINE chat webhook events](https://developers.line.biz/en/docs/messaging-api/receiving-messages/) do not list chat-opening/read-receipt events; [Quick replies](https://developers.line.biz/en/docs/messaging-api/using-quick-reply/) disappear locally after supported actions/new messages. These do not replace server ownership/concurrency checks. The extension is not installed or live-tested.

Root,8October2026. CH054, original overview§46–48 and master§54. Dependencies: active Supabase staff login, existing encrypted Staff ingress, private staff identities, scoped alerts/commands and delivery locks. No Student identities are created.

An authenticated active staff member creates a10-minute one-use binding command in Settings and sends it to Staff OA from their own LINE account. A256-bit random token is purpose-hashed for lookup and encrypted for issuer-only idempotent request recovery; raw LINE identities remain encrypted/hash-indexed. The public status DTO exposes only bound/pending/expiry observations, never technical IDs or hashes. Creation/replay is bound to actor/request UUID; creating a different challenge invalidates older ones. Already-bound accounts must explicitly unlink before replacement. A LINE identity already attached to another staff account is rejected; neither token possession nor LINE text creates staff roles/accounts/grants.

Staff signed durable processing validates the exact command, token expiry/consumption, current active account and both identity uniqueness constraints. Bind/unbind/challenge mutations serialize under a private binding catalog lock and acquire the existing `delivery:STAFF:<staff>` lock before changing identity; started delivery completes first, later delivery observes inactive/new binding. Explicit unlink invalidates all challenges and staff action tokens. Same-user consumed retries are idempotent; another user cannot replay them. All SQL is local to the existing lease transaction; no LINE HTTP in SQL. The setup command needs no Student/ticket routing and is not an AI keyword router.

Settings shows the current binding, temporary copyable command, expiry, refresh and explicit unlink confirmation. Dashboard polling observes completed binding; there is no invented LINE success reply or unconditional notification. UI never displays raw LINE IDs. POST `/api/staff/line-binding/challenge`, GET/DELETE `/api/staff/line-binding` use active self identity, private headers, same-origin/strict bounded JSON and fixed errors. Backend may audit fixed binding event names with no command/identity payload.

Root owns auth/privacy/schema/contracts/process integration. Human sends the command into the actual Staff OA only during deferred live setup. Owned fixtures test real PostgreSQL transactions without live messages. Source does not prescribe token lifetime or command syntax; these are recorded engineering choices.
