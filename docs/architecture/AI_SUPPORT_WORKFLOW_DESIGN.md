## Current gaps and boundaries

The production knowledge producer classifies academic scope and retrieval method, but not support intent. It embeds only the current message, so a device/error follow-up may lose the original Wi-Fi problem. Escalation currently takes the last USER message as its summary, uses GENERAL/MEDIUM defaults and shows every department. Successful delivery is not evidence of a solved problem; Analytics correctly returns unknown AI resolution. Keep existing free gateway, local E5, approved-source selection, confirmation receipts, HUMAN suppression and lease/delivery fences.

Implement three reviewable slices: B1 pure semantic proposal/source validation; B2 private durable context/outcome storage; B3 production producer, owned confirmation/escalation and scoped Analytics integration. B1 alone is unused preparation and cannot complete FlowB/C. B2 migrations must pass owned replay/RLS/advisors before guarded local/DEVELOPMENT activation; production activation is separate. No student/profile/enrollment/grade database is introduced.

## B1: semantic proposal with literal USER evidence

The classifier receives the current question and at most eight recent actual USER messages from this conversation, with ephemeral U0(current),U1…U8 labels. Each text is bounded; backend IDs, technical LINE identity, anonymous codes, staff messages and assistant assertions are excluded. The active department directory contains public code/name pairs only. Delivered assistant guidance is represented as a backend boolean, not evidence of student identity, facts or a successful outcome. One configured FREE_ONLY generation call, no tools, caller cancellation and a bounded stage deadline.

A strict proposal extends the existing router fields with a controlled intent (INFORMATION/TROUBLESHOOT/PERSONAL_CASE/ESCALATE/SOLVED/OTHER), an allowlisted missing-context question, proposed sensitivity/impact, and literal facts. Fact fields are PROBLEM/DEVICE/ERROR/PREVIOUS_CONNECTION/LOCATION/ATTEMPTS/IMPACT/SENSITIVE_DETAIL. Each fact identifies a supplied USER code and a nonempty exact substring quote; its value is that quote, with no generated paraphrase. Unknown fields/codes, duplicate fields, excessive text, malformed output or tool calls are invalid. This prevents invented collected facts; it does not independently certify that a user's reported fact is true.

Backend interpretation requires confidence>=.8. Departments resolve to a fresh active directory entry, with the established REGISTRATION→REGISTRAR alias. Categories derive from the accepted department code, not arbitrary model category strings. Conflicting or unknown proposals cannot route a ticket. User-authored text remains untrusted evidence, never instructions. A model needsTicket flag only recommends a human path; it never grants create_ticket authority. Personal cases explain the absence of personal record access and offer escalation without asking for a university-wide student record import.

Clarification uses fixed Thai templates for DEVICE/ERROR/PREVIOUS_CONNECTION/LOCATION/ATTEMPTS only when relevant and not already supplied. No generic program/cohort question for a Wi-Fi device problem. Unclear intent retains a bounded clarification or the existing safe handoff. INFORMATION proceeds to existing internal knowledge selection; TROUBLESHOOT collects missing details then searches reviewed guidance. A continuation query combines the source-selected original problem and literal supplied facts within the embedding query budget. It never treats assistant text as user facts or invents current policy, commands, URLs or unofficial procedures.

Priority/severity are backend-owned: one-user/device reports default MEDIUM/NORMAL; a grounded report of multiple affected users may propose HIGH/ELEVATED, explicitly reported rather than verified. CRITICAL remains dependent on an independently verified current incident/service disruption; a model's urgency or a single unverified university-wide claim cannot set it. Sensitivity never drops below the existing server minimum: personal cases are at least SENSITIVE; a grounded restricted risk is RESTRICTED. Missing or conflicting risk evidence yields a conservative review path rather than an automatic sensitive-data reply.

## B2: private source-bound persistence and explicit outcome

Add private.ai_support_state keyed by conversation, holding encrypted validated facts, backend category/department/priority/severity/sensitivity, source message identifiers/digest and the last contributing AI job. Add private.ticket_support_contexts keyed by ticket for the encrypted collected context copied during confirmed creation. Add private.ai_support_outcomes for an immutable, idempotent USER_CONFIRMED_SOLVED or USER_CONFIRMED_ESCALATED event, linked to the owned session/conversation/source confirmation and scoped department/sensitivity. No plaintext contact details or account credentials in public fields, DTOs or logs. Private tables use RLS/revoked public roles and exact foreign ownership constraints; indexes follow actual lookup/scope/date predicates.

Persist advice only inside an eligible owned AI-job finalization after comparing the current exact USER source digest and department/risk context. Takeover, closure, additional relevant USER text, changed directory or lost lease discards stale advice. HTTP stays outside SQL. A result already saved is replayed only after the same fences. An answer job or successful LINE send cannot create a solved outcome. Old jobs/results without support metadata remain compatible but confer no new outcome/confirmation authority.

## B3: production actions, troubleshooting and confirmed escalation

Execution checkpoint B3A: `createSupportProducer` uses the unchanged knowledge producer for Staff/legacy snapshots, and the configured Student worker enables a short private `SupportStateSnapshot`. A strict optional private result envelope binds the original source/directory/minimum/guidance/proposal; source metadata never enters the public message/browser DTO. Finalization and dispatch require current exact source/state, in addition to existing reviewed knowledge/lease/HUMAN fences. Continuation retrieval uses literal source-selected problem/details; only a source-validated active canonical department can relax the department label check, while student/year/cohort/applicability grounding remains unchanged. B3B supplies appropriate owned actions and confirms only prior verified troubleshooting guidance; generic answer delivery alone does not authorize a solved outcome. [Current evidence](../reports/AI_SUPPORT_PRODUCER_REPORT.md).

Bind B1 into the existing configured producer, retain the overall worker deadline and degrade safely when classification is unavailable. Support metadata is a strict optional extension to existing durable result variants; public Staff knowledge projection continues to expose only verified answer/citations and no collected private facts. Source-compatible finalization creates relevant backend-owned, expiring one-use actions rather than unconditional Contact/New choices on every reply. Ambiguous context retains existing explicit context choices.

After a delivered eligible troubleshooting answer, offer a short solved/still-unresolved choice. SOLVED only offers a backend-owned confirmation; consuming it validates the same owner, conversation/source, mode/revision, delivered guidance and exact current state, then records USER_CONFIRMED_SOLVED and resolves that AI conversation without creating a ticket. New topics still create separate contexts. A text statement alone or model intent never silently closes a ticket or records a success.

Unresolved/personal/explicit-contact cases recommend one accepted department with a deliberate confirmation and a choose-another-department alternative. Fresh backend resolution must still allow choosing another active unit. Reuse the consumed ESCALATE postback and tool receipt; arguments cannot supply authorization. At creation, revalidate state/source and copy the collected encrypted context; write server-derived category/subcategory, summary from an actual USER problem quote, priority/severity/sensitive_level. Notifications use the existing sensitivity rules, binding/delivery fences and idempotent outbox. Unclassified legacy contact retains safe manual department selection.

The manual Contact path must preserve an existing encrypted/validated support sensitivity minimum even before full B3B enrichment. A corrupt/mismatched state fails CONFLICT instead of creating a GENERAL ticket. Apply this minimum at ticket INSERT before notification selection; no caller/model sensitivity argument. A new USER fact may invalidate old advice for enrichment, but cannot lower a valid prior sensitivity floor.

Analytics reports observed outcomes and the explicit denominator: confirmed solved / (confirmed solved + confirmed escalated) within the requested Bangkok date window and authorized department/sensitivity scope. Zero observed outcomes remains unknown, not 0% success. Unclassified outcomes are visible only to the global authorized administrator and cannot leak across departments. The dashboard labels this as confirmation-based evidence; it does not imply every unanswered session was solved. Worker heartbeat and verified incident system/location enrichment remain separate tasks.
