## B1 frozen pure contract

`lib/incidents/context-resolution.ts` exposes `planIncidentContext(claims, departmentCode)` and `resolveIncidentContext(plan, results)` with strict bounded contracts in `context-contracts.ts`. Claims are exactly `{system:string|null, location:string|null}`; literals preserve their complete source value without trimming, truncation, case folding, alias matching or fuzzy matching. Invalid inputs fail explicitly. The eventual private decoder is the only authorized production caller; pure resolution itself does not prove source eligibility.

The plan returns at most3 fixed attempts with slots SYSTEM_CODE/SYSTEM_NAME/LOCATION and `StructuredSearchRequest` values. System code matches exact `university_systems.code` (max200); name matches exact `name` (max500); location matches exact `university_services.location` (max500). A longer literal skips the incompatible selector without truncation. Fixed limit20 and scope: familyCodes=[] (the existing unrestricted-family vocabulary, never null), supplied active ticket department code, audience=ALL, studentType=ALL, all semester/program/curriculum/cohort/year/asOf selectors=null, historical=false. Root adds location to the strict structured query/selector contract; no SQL/URL/model/network runs in the pure matcher.

Resolution accepts exactly one corresponding search result per planned attempt. Revalidate READY evidence through the existing structured evidence validator and exact payload predicate. Mismatched datasets/selectors, invalid/duplicate contradictory rows, non-EMPTY/READY statuses or incomplete results cannot grant a known key. System attempts are considered together: known only if all successful matching rows identify one logical familyId/versionStream/code and one consistent name. A failed/ambiguous code or name attempt makes that system unknown; EMPTY plus a unique valid match is allowed. Location is known only when exact matching rows identify one familyId/versionStream/location. Different source families/streams with the same label stay ambiguous. Unknown is null; location and system resolve independently.

Keys are `SYS:` or `LOC:` plus a domain-separated SHA-256 canonical digest of the full familyId/versionStream/source scalar tuple, max68 ASCII characters. Do not rely on globally unique source codes or truncate Unicode source values. These keys and complete source proofs remain private; public incident/similar-issue DTOs omit both.

## B2 integration gates — remaining root work

Before wiring the matcher, freeze private proof storage and catalog/time freshness. A known context and a previously unknown exact lookup must become stale when publication, source eligibility, amendment/currentness or effective day changes. Similarity reads cannot use stale keys; detection must requeue/revalidate rather than retain an obsolete source identity. The B2A contract below fixes a coarse private catalog epoch plus a Bangkok evaluation day for owned-disposable verification; this is not normal/remote schema activation or runtime acceptance. Root accounts for protected source/provenance writers and publication/incident/job lock ordering in that infrastructure gate.

Local E5 stays outside SQL. Final worker state uses shared knowledge catalog → incident catalog → sorted conversations/tickets → job locks, then rechecks revision/lease/immutable support owner/digests/source proof before atomic vector/context persistence. Missing/no-claim facts and valid exact EMPTY/ambiguity may prove an unknown value; corrupt support or unavailable/incomplete source evidence grants no fresh vector/proof and must retry rather than silently become unknown. Never guess aliases. Retained memberships remain history: changed source context may block extension, never silently delete or rewrite old membership. Fresh Staff scope and privacy checks precede reads; technical proof/quotes/keys never enter operational logs or public DTOs.

## B2A frozen infrastructure contract

Root authors one additive CLI-generated migration for owned replay only before B2 runtime activation. Two private RLS tables: `structured_selection_epoch` is a seeded id=1 monotone bigint revision with DB-clock update time; `incident_context_proofs` has ticket FK/PK, ticket revision, nullable support binding digest, READY/BLOCKED state, requires_catalog flag, nullable epoch/Bangkok evaluation date and nullable encrypted proof. Catalog/day are present together exactly when requires_catalog. READY with an existing support copy requires authenticated encrypted proof; READY NO_COPY uses null binding/proof and null known keys. BLOCKED cannot authorize a vector. Service gets epoch SELECT/UPDATE(revision,updated_at), proof SELECT/INSERT/UPDATE(nonidentity columns), no DELETE, and no browser privileges. Epoch UPDATE enforces old+1 and DB time under the exclusive catalog guard; no key mutation/reset.

The existing catalog statement guard advances the epoch and atomically requeues active requires_catalog proofs, including previous exact misses/ambiguity and blocked sources. It takes the existing try-exclusive advisory lock before epoch/job mutation, never waits after a direct writer's row locks. Add the same guard to immutable private structured provenance/effects/publication receipts and import-job INSERT/DELETE/TRUNCATE plus UPDATE of checksum/source_metadata_encrypted/publication_status; these are dependencies read by exact search. Existing public family/document/relationships/departments/seven typed tables retain their guard. Conservative no-op statements may invalidate; unpublished staging inserts may invalidate but cannot grant a source. All changes roll back together. Publication performs no incident-catalog/conversation locks; no HTTP/E5 occurs in triggers. Existing sidecar history is never deleted. An AFTER INSERT immutable support-copy trigger queues its exact owned ticket so a late copy invalidates earlier NO_COPY evaluation.

`incident_detection_jobs` gains nullable context_epoch/context_evaluation_date request markers to bound repeated day refresh. `refresh_incident_context_jobs()` considers at most100 active stale requires_catalog proofs in sorted ticket order, uses job-row SKIP LOCKED and requeues only when the epoch/day request markers differ. It does not reset repeated same-day failures or live PROCESSING leases; source-catalog invalidation explicitly revokes obsolete leases. This helper is infrastructure only until the worker calls it. Existing migration/worker behavior remains compatible until integration; retained active tickets are queued once by the additive migration.

Pure `decodeIncidentSupportSource(ticket, copy, key?)` in `context-source.ts` accepts strict bounded ticket identity `{id,conversationId,sessionId,departmentId}` and nullable exact copy `{ticket_id,conversation_id,line_session_id,source_digest,state_digest,context_encrypted}`. It returns NO_COPY with null claims/binding; READY with complete exact SYSTEM/LOCATION claims, source/state digests and domain-separated binding digest; or UNAVAILABLE without raw values/errors. Existing copy envelope identity/department/owner/sourceDigest, raw serialized support hash, declared sensitivity and unique collected facts equal to proposal facts must agree. Raw JSON support hash precedes schema parsing; never hash reordered parsed data. The immutable copy was grounded by the original authorized writer, so this decoder does not reclassify a HUMAN ticket or invent registry eligibility. No database/network/logging/side effects. Existing unreadable/tampered/cross-owner/cross-department copies fail UNAVAILABLE. All outputs remain private. Old valid copies without SYSTEM stay compatible.

B2B runtime must authenticate stored proof and exact support binding against current tickets/copies before using its keys; SQL epoch/day alone does not authenticate an encrypted proof. Known and negative lookups are freshly performed under the shared catalog lock, with explicit statuses: NO_COPY/NO_CLAIM/EMPTY_EXACT/valid source ambiguity may be null; unavailable/incomplete/corrupt data is BLOCKED/retry. Worker and Staff reads omit BLOCKED/stale candidates, queue bounded refresh and retain historic memberships. This infrastructure gate is not runtime enrichment acceptance or authorization to apply normal/remote schema before complete B2 gates.
