## Verified repository and platform constraints

Existing Supabase SSR clients use PKCE; password login/recovery and active staff_profiles authorization remain. Installed auth-js2.117.2 accepts custom providers and explicit linkIdentity. Pending applicants have an authenticated Auth user but no active institutional Staff profile, so requireStaff cannot gate their self-service endpoints. No onboarding API/schema or OAuth initiation/callback currently exists.

Use Supabase custom OAuth2 provider `custom:line-staff`, email_optional=true, PKCE enabled, scopes openid/profile without email. LINE authorization/token/userinfo endpoints are fixed platform configuration; LINE Login and Staff Messaging channels must be under the same LINE Provider. Supabase owns provider secret/token exchange. Do not use a Messaging API channel secret as a Login secret, invent an email or rely on display-name/email/staff-code matching. Explicitly link existing password accounts while signed in. Callback must return to that same Auth subject for link mode.

Sources checked29October: [custom OAuth providers](https://supabase.com/docs/guides/auth/custom-oauth-providers), [manual identity linking](https://supabase.com/docs/guides/auth/auth-identity-linking), [LINE Login reference](https://developers.line.biz/en/reference/line-login/), installed Next16 route/cookies and SDK guides. ## Identity and admission

The API obtains the current Auth user with server getUser, never a user-supplied subject or editable metadata. A server-only VerifiedStaffAuth consists of Auth userId plus an optional `{identityId,subject}` for exactly one `custom:line-staff` identity. Require UUID identity_id, matching user_id and LINE sub consistent with provider identity. Recheck the matching auth.identities row and provider_id in the business transaction; browser claims alone confer no authority.

Anonymous/self context preserves the frozen DTO: authenticated, lineLinked, staffActive, loginAvailable, canReview, application and active department options. A logged-in unlinked account can explicitly link LINE but cannot submit. Existing active Staff goes to its account; no new application/profile or role change. An existing inactive Staff profile is blocked with a fixed STAFF_ACCOUNT_INACTIVE error for manual SuperAdmin review, not silently reactivated or fabricated as an application. The current UI may show a generic unavailable state for that error; a specific copy/state is a coordinated frontend follow-up.

Configure `LINE_STAFF_LOGIN_ENABLED` only after hosted provider/manual linking/callback setup and same-provider confirmation. Missing configuration means unavailable, never a fake login. Provider credentials stay in Supabase. Existing password recovery remains available independently.

## Private application model

Reuse public.staff_profiles/auth.users/auth.identities and private.staff_line_identities. Add private.staff_applications with one application per Auth user for this V1 workflow: id, auth_user_id, nullable auth_identity_id, immutable line_subject_hash/encrypted subject, applicant_name, staff_code, requested_department_id, approved_department_id, status, revision, timestamps, reviewed_by/reason and submitted requestId/digest. Identity FK deletion must retain application audit while removing stale live identity authority; approval requires a current matching identity. Add private action receipts keyed reviewer/requestId with immutable application/action/payload digest and response snapshot. No public grants/RLS policy for either table; server API projects only frozen browser DTOs. Index every referencing FK and status/time/id list path.

Applicant name/code/department are claims for human review. No self-selected role, sensitivity flag or arbitrary grant field is accepted. One application remains the audit record; rejected/suspended are terminal in this V1 UI. Reapplication/reactivation is an explicit future administrative workflow, not an automatic privilege restoration. A pending same-subject LINE re-link may refresh only its identity pointer/revision after fresh authenticated proof; never transfer it to another subject/account.

State machine: PENDING→APPROVED or REJECTED; APPROVED→SUSPENDED. Every mutation uses current active SUPER_ADMIN, expected revision and immutable idempotent requestId. Concurrent reviewers yield one transition; retry of a committed identical request returns the original response, changed body conflicts. Refreshed auth/role/scope remains mandatory before serving a receipt. Approved/suspended personnel codes reserve their exact trimmed value; duplicate claims require administrative account review, never implicit merging or code-based identity verification.

Approval chooses an explicit active final department, creates only base STAFF with sensitive/restricted flags false, and does not infer employment from LINE. It never upgrades an existing profile. Reject grants nothing. Suspend deactivates the approved Staff row and OA binding under existing access/delivery locks and triggers; accepted/SENT history is retained. Existing auth password sessions may remain authenticated but lose all institutional case authority immediately through fresh Staff/RLS checks.

## OA binding and callback

LINE Login proves account ownership; approval supplies institutional authority. Only an approved/current active Staff account can bind a verified same-provider LINE subject. Keep global technical subject uniqueness and the existing Staff access/delivery lock order. Never overwrite another account's binding or silently revive an explicitly inactive/unfollowed binding. If binding is OAuth-backed, retain the auth identity reference so unlinking can invalidate that channel authority; old explicit-challenge bindings retain their separate proof. Read-only context endpoints do not bind/reactivate identities.

Approval binds a new OA identity only when trusted deployment options explicitly set sameProviderConfirmed=true; login availability alone is insufficient. Auth table reads require SELECT/REFERENCES only, without acquiring UPDATE privileges to row-lock Auth-owned tables. Recheck current identity immediately before granting employment; application/binding FKs fence deletion. Subsequent unlink revokes OAuth OA authority while retaining human-approved employment and audit. Explicit challenge rebinding clears the OAuth FK and keeps its independent proof.

Staff OA welcome/on-add message can contain the public `/staff/apply` URL through LINE OA's normal greeting configuration. Prefer that platform capability to inventing an unbound private-notification recipient or relaying Student data. After approval existing scoped notifications/ACCEPT/Dashboard links apply. No onboarding message can contain ticket/Student details.

OAuth initiation/callback reuse Supabase PKCE cookies. A short-lived HttpOnly/SameSite=Lax encrypted flow cookie binds discriminator/version, random nonce, mode, fixed next target, expiry, SDK PKCE flowId and expected Auth subject for explicit link. Supabase manages its own reserved OAuth state/PKCE. The installed SDK always returns its flowId, while appending sb_flow_id to callbacks is opt-in; use the stored flowId even when that parameter is absent, and reject a supplied mismatch. Only fixed next paths `/staff/apply`, `/staff/application`, `/dashboard` are allowed. Build callback from trusted APP_BASE_URL (HTTPS or loopback development), never arbitrary Host/next/provider URLs. Reject duplicate/bad code/error parameters, consume browser intent before one-time PKCE exchange and never log code/tokens/provider error strings. A callback cannot grant Staff access itself.

New binding FK checks precede application row locks; reload identity/status/revision after acquiring those fences. This avoids an app-row/Auth-delete inversion without granting Auth table UPDATE privileges. A pending same-subject relink updates only a changed identity pointer/revision and one private SYNC_IDENTITY receipt, then uses the new revision for review. Existing fail-fast staff-chat access guards may reject a concurrent Auth unlink with 40001; that transaction rolls back and an explicit retry after sync succeeds. Owned tests exercise this outcome; no retry loop, partial grant or automatic inactive revival.
