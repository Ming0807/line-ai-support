## Gaps confirmed by source reading (not invented)

G1 duplicate composers with divergent semantics: `inbox.tsx` composer vs `ticket-actions.tsx` composer (`/tickets/[id]` server transcript is a second, non-live copy of the thread).
G2 note composer `maxLength=3000` in `inbox.tsx` — contract is 4000 (`noteChatInputSchema`).
G3 `inbox.tsx submitMessage` clears the entire draft on success of the old request (`setDrafts(...[key]:'')`) — a new draft typed while an uncertain request finishes gets silently destroyed; also typing a new text deletes the pending retry entry (`updateDraft`) and a fresh submit silently creates a NEW requestId for the same uncertain outcome.
G4 `loadEarlier` has no fence/serial/catch-up logic; `refreshThread` merge can leave a sequence gap invisible when a burst exceeds the 50-message window (example proven: old `[s51..s100]`, refetch returns `[s151..s200]`; merged union hides the hole and the older-history button loads `beforeSequence=51`, skipping `[s101..s150]`).
G5 list fetches race: effect path aborts its controller but `invalidate()`, manual refresh and post-submit refetch run unfenced — a stale older-query response can overwrite the newest list.
G6 missing URL deep-link for view/filters/page (only `?ticket=`), no recovery path when the server reports zero/out-of-range pages, and unknown pagination not surfaced distinctly.
G7 inbox exposes only "รับเรื่อง (accept)"; resolve/close/reassign/reopen live solely on the detail route UI, so the workspace context pane does not show permitted lifecycle actions per `TicketDetail.permissions`.
G8 no real path from Inbox to the shared-incident evidence review (department/category equality is not an incident); `/incidents?department=<uuid>` genuinely exists (`incidentQuerySchema` supports `department`), nothing links there today.
G9 attachments markup exists but long-file-name overflow and non-READY states are weak; no regression pins "no href unless READY+downloadUrl".

## Architecture decision for task 2 (one conversation workspace)

- New client helper `app/(dashboard)/tickets/[id]/chat-thread.tsx`: the single conversation engine (fetch/merge/read-ack/load-history/submit reply+note with immutable writes/delivery evidence/attachments/assist-panel draft application). Two mount types: Inbox center pane and `/tickets/[id]` main column (server initial data via `readThread(staff.id, id, {limit:50})`; no extra client first-fetch).
- New pure module `app/(dashboard)/tickets/[id]/chat-thread-state.ts`: `mergeThreadMessages` (id-dedup, sequence sort, mid-gap cursor `firstCatchUpBefore`), `pendingWriteDecision` (immutable pending write per actor+ticket+kind), submit outcome classification (statuses × network × invalid-JSON). Re-exported from `inbox/controller.ts` when shared with root tests.
- `ticket-actions.tsx` becomes the only owner of lifecycle actions (accept/resolve/close/reassign/reopen) with pre-mutation recipient-context confirmation; reply composer/AI panels removed from it (assist panels move with the composer into `chat-thread.tsx`; texts/labels unchanged). Optional `onActionCompleted` callback lets Inbox refetch thread+list after client-side success (detail route keeps `router.refresh()`).
- `page.tsx` keeps every server panel (metadata byline, history, support context, similar issues, deliveries, facts); its transcript section is replaced by `chat-thread.tsx` (server initial data), so no second transcript/composer remains.
- Naming: new helper files inside `/tickets/[id]/` use the mandated `chat-*`/`ticket-action-*` prefixes; `inbox/**` keeps existing file names.
