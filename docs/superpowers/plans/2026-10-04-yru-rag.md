## Architecture and ownership

Preserve Next/Auth, raw-body verified durable inbox, the conversation router, transactional ticket service and outbox. Inbox processing remains a short transaction: resolve/store the user message and prepare a durable AI job. A separate worker snapshots context, commits, performs provider/embedding HTTP, then commits only if the job lease and conversation mode/revision remain eligible. No AI HTTP occurs inside a business transaction or while holding its conversation lock. Root owns this integration and the database/retrieval/security boundaries.

Use the existing provider registry and encrypted credentials. Model registry gains explicit GENERATION/EMBEDDING purpose and expected embedding dimensions; existing models remain GENERATION. Dashboard remains the configuration path. There is no guessed embedding model/dimension. An embedding adapter validates returned dimensions/finiteness and the model fingerprint must match indexed chunks; incompatible vectors are never compared. Native OpenAI embedding HTTP is isolated behind a registered adapter and tested with fake transport.

Luna MAX owns only the embedding HTTP adapter/tests/report. Luna HIGH owns only pure section/page-aware chunking/tests/report. Root freezes their interfaces before delegation, then reviews and integrates. An independent MAX review follows meaningful PG/worker tests.

## Data and retrieval contract

- Add document_families, documents (one row per version), document_relationships and knowledge_chunks, preserving master guide names/provenance. All are RLS-enabled with explicit server grants and no browser DML; admin services will authorize safe DTOs. Anonymous answers use PUBLIC sources only.
- Document metadata includes family/department/type, audience/student type, academic year/semester, program/curriculum/cohort, effective dates, authority, official provenance, checksum/storage/source URL, review/approval and extraction flags. Collection time is never an effective date. Real187-resource corpus remains unpublished; begin staging only shortlisted eligible sources.
- Separate an explicit version stream from applicability. Annual calendar replacement may advance academic year within the same reviewed audience/program/cohort/semester stream; cohort-specific documents remain separate. The publish service in M7 validates replacement targets and scope, rather than inferring replacement from year alone. Additional/amendment sources remain separate and use typed relationships.
- Current search requires approved, ACTIVE/current, PUBLIC, official, extraction-reviewed and effective documents. Historical search is explicit and permits approved superseded versions for the requested reviewed year/date. Missing scope/ambiguous applicability yields clarification. Never silently combine incompatible audiences or curricula.
- Eligibility and authority selection occur before similarity ranking. Retrieval compares only matching embedding fingerprints/dimensions. Variable-dimension pgvector storage avoids inventing a model; indexes are added only for an explicitly configured dimensional cohort. Small shortlisted corpora can use exact distance over the prefiltered set while that index configuration is pending.
- Citations come from retrieved document/chunk IDs and backend source/page/section metadata. Model-generated URLs/page numbers are not accepted. Finalization revalidates cited versions and current eligibility; a superseded source cannot complete a new current answer. No evidence means clarification/handoff, not invented university policy.
- Dispatch rechecks evidence under session advisory locks without an open transaction across LINE HTTP. M7 publication/eligibility writers must take `knowledge-family:<family UUID>` transaction locks in sorted order, then `knowledge-document:<document UUID>` locks in sorted order before row locks. Family locks cover new same-stream historical versions as well as changes to an existing cited document. Suppressed/pending AI outboxes never become assistant history; only confirmed SENT answers do.

## Durable job and tool boundaries

AI jobs are unique per routed user message, ordered per conversation, leased with database wall-clock checks and finite retries. Prepare, provider-result persistence and business finalization are distinct stages so a stored result can finalize without paid regeneration. Idempotent tool receipts prevent duplicated ticket effects. Stage transitions, recipient/ownership and HUMAN eligibility are backend-enforced.

Root registers real search_knowledge, route_department and create_ticket executors using validated arguments plus trusted job/session/conversation context. search_structured connects to the fixed M8 registry when available; absence cannot produce fabricated structured records. No model-controlled SQL/table/URL/credential exists. Ticket actions use existing service/state machine and controlled escalation rules. An AI proposal alone cannot bypass conversation ownership or takeover policy.

Keep M4 context choices for ambiguous old/new requests. HUMAN messages continue to their selected ticket without AI jobs. Explicit new topics may run AI while an older HUMAN ticket remains active. Initial/new AI text prepares a job; missing configuration/evidence yields a bounded neutral clarification/handoff instead of a false generated answer.
