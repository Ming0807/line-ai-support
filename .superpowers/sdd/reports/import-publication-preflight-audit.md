# M7 publication preflight audit

**Date:** 6 October 2026
**Scope:** Read-only audit of `KNOWLEDGE_IMPORT_DESIGN.md`, master §§38–42/49–50/60–61, Task4 in `docs/superpowers/plans/2026-10-04-yru-knowledge-import.md`, the listed original sources, and current SQL/application source. No code or database was changed. Root owns the contracts, DB/auth/integration, and next publication implementation.

## Finding

The schema and review/version-preview prerequisites exist, but there is no approval endpoint or publication transaction yet. Existing SQL can store documents, chunks, and relationships; the current application can save a private reviewed draft, resolve candidate actions, and produce a review-bound chunk plan. Those pieces do not create approved documents or make `AMENDS` / `CANCELS` relationships affect retrieval. A new additive approval receipt and a single carefully fenced publication service are still required.

The main implementation risks to settle in root's frozen contract are:

1. Task4 says mark `knowledge_import_jobs` `COMPLETED`, but its current SQL status check only permits `READY` / `FAILED`, and the current import design explicitly says these describe source/extraction availability rather than approval. Publication completion needs a separate receipt/status contract or an explicitly additive status change; do not overload `READY` / `FAILED` silently.
2. Master §41's example mapper has six dataset identifiers and omits `university_systems`. Current `types.ts`, import design, and M8 board contract require seven fixed datasets. The seven-code current contract must govern M8.
3. Master §42 says unknown structured data requires Admin approval without specifying the resulting storage mode. The original versioning source says RAG is the fallback until a structured schema exists. Current reviewed design resolves this as retain/review the candidate, use RAG when selected, and block unsupported `STRUCTURED` / `BOTH`; no dynamic DDL.

## Existing database contracts

The current physical model is in `supabase/migrations/20261004125859_knowledge_rag.sql`:

- `public.document_families`: UUID `id`, unique uppercase `code`, `name`, `category`, and `default_storage_mode` constrained to `RAG | STRUCTURED | BOTH`.
- `public.documents`: family and nullable department FKs; reviewed identity/scope fields (`title`, `document_type`, `version_name`, `version_stream`, academic year, semester, audience, student type, program/curriculum/cohort); published/effective dates; `status`, `is_current`, `authority_level`, `approval_status`, `approved_by/approved_at`, official-source/extraction/review/visibility/archive flags, source URLs/path/MIME, immutable-source checksum, `supersedes_document_id`, and integer `revision`. SQL requires `approved_at` when approved, and any `ACTIVE`/`SUPERSEDED`/`EXPIRED` document to be approved, extraction-reviewed, not requiring review, and to have `effective_from`. `is_current` implies `ACTIVE`. `(document_family_id, version_stream, checksum)` is unique; partial unique `(document_family_id, version_stream)` applies when `is_current` is true. Thus a replacement must clear the old current row before inserting its new current row.
- `public.document_relationships`: `source_document_id`, `target_document_id`, and one of `SUPERSEDES | AMENDS | ATTACHMENT_OF | RELATED_TO | CANCELS`, with no self-link and unique source/target/type. Current SQL does not enforce relationship direction semantics, action applicability, cycles, effective intervals, or matching review scope; the publication service must enforce those rules.
- `public.knowledge_chunks`: document/index, nullable page/section, content, `requires_review`, generic vector/dimensions/fingerprint. The E5 migration adds the generated `embedding_e5 vector(384)` projection for the fixed local fingerprint. `20261006044000_knowledge_source_locations.sql` adds `source_locations jsonb NOT NULL DEFAULT []` (array, at most 16 objects, ≤65,536 serialized bytes, known `kind`) and nullable `passage_token_count` constrained to 1–512. SQL deliberately does not validate detailed ranges, format alignment, or recount tokens. Application approval must require nonempty, strict, source-format-consistent locations and the exact plan/token binding for every newly published chunk. Existing `[]`/NULL rows remain legacy evidence.
- Current cohort and chunk bounds already exist: chunk index 0–1,999, content 1–6,000 characters, vector dimension/fingerprint pairing, nonzero vector; E5 vectors additionally require normalized 384 dimensions. Keep existing cohorts and old rows; do not backfill invented locations or remove old vectors.

Private import tables are additive and RLS-enabled:

- `private.knowledge_import_jobs` (`20261005093910_private_knowledge_import_staging.sql`) binds UUID job/original, creator, SHA-256 checksum, one of five formats, backend/key version/byte length, encrypted original or private-storage reference metadata, `status READY | FAILED`, job `revision`, and parser `error_code`. Its immutable trigger prevents changes to original identity/bytes/metadata but permits workflow fields to change. Its SQL status check has no `COMPLETED` value.
- `private.knowledge_import_revisions` (`20261005172910_private_knowledge_extraction_revisions.sql`) is keyed by `(job_id, revision)` and stores base revision, actor, `PARSED | EDITED`, extraction checksum, encrypted extraction/analysis/review. An update trigger rejects mutation. It has no app delete path.
- `private.knowledge_import_reviews` (`20261005185744_private_knowledge_review_receipts.sql`) is keyed by `(job_id, review_revision)` and stores the bound job/extraction counters, actor, payload hash, encrypted review and timestamp. It references the extraction revision. Update is rejected by trigger. The v2 `chunkPlan` digest/chunker acknowledgment lives inside the authenticated encrypted payload, not a SQL column.
- `private.activities` stores optional ticket, actor, action, JSON metadata and timestamp. Publication can append an audit row in its transaction.
- There is currently no publication/approval receipt table, `published_document_id` on a job, or status column that identifies successful publication.

Grant boundary: knowledge public tables have RLS enabled, revoke all for `PUBLIC`, `anon`, and `authenticated`, and grant all to `service_role`. Jobs also revoke browser roles and grant all to `service_role`. Revisions and reviews revoke all (including `service_role`) then grant only `SELECT, INSERT` to `service_role`, with update-blocking triggers; activities are private/RLS and service-role only. `service_role` is the DB boundary for server code; active `SUPER_ADMIN` authorization must still be performed in application code before reads/decryption and again in the final transaction. The existing `withImportAdminTransaction` sets a 5-second statement timeout and 3-second lock timeout and checks that active profile/role inside each transaction.

## Existing application contracts and gaps

Task4 has completed candidate and private-review prerequisites, not effects:

- `review-schema.ts` persists exactly five actions: `NEW_FAMILY`, `ADD_ADDITIONAL`, `REPLACE_CURRENT`, `ADD_HISTORICAL`, `AMEND_EXISTING`. It binds exact target ID/revision for replacement/amendment; `relationship: 'CANCELS'` is a separate field permitted only with `ADD_ADDITIONAL` and an exact target. Candidate lookup in `version-resolver.ts` is read-only and explicitly not publication authorization.
- `getImportChunkPlan` and `prepareImportChunkPlan` re-read the saved review, authorize an active super admin, prepare from the validated original/extraction outside the final short DB transaction, then lock the job `FOR SHARE` and fresh-check job/extraction/review counters. Saving v2 acknowledgment recomputes the plan outside SQL and appends a new encrypted review receipt through a final job lock/CAS. These routines stop before vectors or publication.
- `prepareEmbeddedKnowledgeChunks` is an older helper for page-only `chunkPages`; it rejects review-needed pages and returns vectors. It is not a located-plan publisher and cannot satisfy provenance by itself. New publication must embed the exact bounded located plan (including final overlap text) outside any business SQL transaction, check fixed E5 model/revision/fingerprint/dimension/norm/cardinality, and only persist the matching plan's content, tokens, locations, and vectors together.
- No `app/api/knowledge/approve/route.ts` or `lib/imports/structured-mapper.ts` exists in the current tree despite the older master guide naming them. `STR-01` is planned and `STR-02` is HELD. There are no migrations defining the seven structured tables. Consequently RAG-only publication can be the first slice; `STRUCTURED` and `BOTH` must fail closed until their fixed registry, mappers, schema, and atomic integration are accepted.

## Version actions and effects required

The Task4 resolver sees metadata and target revisions; publication must re-read and validate all action facts while holding the final locks:

| Action | Required atomic effect |
|---|---|
| `NEW_FAMILY` | Require family absent and reviewed family name/category; create the family as ordinary data, then the approved document and its located chunks. A family-code lock or unique-conflict recovery is needed because the existing family-ID advisory lock cannot be chosen before this new row exists. |
| `ADD_ADDITIONAL` | Require the current stream to be free across the entire family, including other departments/scopes. Insert a separate approved document/current stream and chunks; do not alter the base. |
| `REPLACE_CURRENT` | Require exact reviewed approved `ACTIVE` current target and same department/type/stream/non-year scope. Recheck target `revision`; change target to `SUPERSEDED`/not-current and increment revision, insert the new approved/current version, set `supersedes_document_id`, and insert `SUPERSEDES` from new source to old target. Preserve the old document/chunks. |
| `ADD_HISTORICAL` | Insert the approved historical document and chunks without modifying an existing current target. Define status/current treatment so it is reachable only through an explicit matching historical/as-of query and never leaks into ordinary current retrieval. |
| `AMEND_EXISTING` | Require exact current approved base, matching full scope and academic year; reject amendment/cancellation chain targets. Insert an approved `ACTIVE`, `is_current=false` amendment instrument and `AMENDS` from new source to base. Keep the base current. Retrieval must include the base and every applicable active amendment before similarity ranking. |
| `CANCELS` whole-document relationship | This is the reviewed `ADD_ADDITIONAL` cancellation instrument, not a sixth ordinary action. Require exact approved target ID/revision, matching scope/year and effective interval; insert approved `ACTIVE`, `is_current=false` instrument with `CANCELS` from new source to target. No partial/provision-level or cancellation-of-cancellation effects. After its effective date, cancelling one amendment excludes that amendment but keeps the base and other applicable amendments; cancelling the base makes the rule group inactive. As-of retrieval before the cancellation date retains the formerly applicable rule. |

These shapes and direction are specified in `DEC-025` and Task4. Candidate revisions are not locks: final checks must reject stale target/family/stream, ambiguous or mismatched scopes, unresolved required warning/sensitivity, and lost applicability. Every action must insert the same-version chunks, required relationships, audit event, and success receipt in one transaction or leave none of them.

## PUBLIC privacy, version eligibility, and queue invalidation

The review schema permits incomplete nullable metadata, false attestations and warning dispositions because a review draft is not publication consent. The publication gate needs a separate strict allowlist of requirements:

- all required trusted metadata, active actor, current saved v2 review bound to the exact job/extraction/review counters, all required attestations true, current target/action selection, valid dates/authority/provenance, exact acknowledged chunk plan, and successfully prepared vectors;
- no unresolved/blocking extraction, source, applicability, or sensitivity warnings for `PUBLIC`; original checksum/source authority must be verified and the stored extraction/edit revision and analysis must match the acknowledged plan;
- detected sensitive categories (`STUDENT_RECORDS`, phone, personal email, grades, medical, personal finance) cannot be made public by marking a warning false-positive or checking an attestation. Correct/redact and reanalyze into a new extraction revision, or retain as `INTERNAL`/`RESTRICTED` under staff scope. Audit only category/reason codes, never matched personal details;
- internal/restricted content still needs active review and scoped access; it must not enter public retrieval or answer citations.

`searchKnowledge` currently filters eligibility before vector similarity for current/effective/public/official/reviewed/non-archive documents and cohort, which is the right order for standalone documents. But it does **not** consult `document_relationships`: current retrieval excludes `AMENDS` instruments because they are `is_current=false` and does not combine them with the base; a `CANCELS` relation does not exclude its target after the effective date. Historical/as-of search likewise has no cancellation/amendment relationship semantics. Implement relation applicability in the materialized eligible-document/rule-group set before ranking, with tests for two amendments, inactive/out-of-date/scope-mismatched amendments, cancel-one/cancel-base, and pre/post-effective historical queries.

`runOutboxCycle` holds a delivery/session lock, then `verifyAIOutboxEvidence` locks cited family IDs in sorted order followed by cited document IDs, re-retrieves, and compares exact cited chunk/document revision/content/metadata/location evidence. Locks are session-level advisory locks and are released in reverse order after LINE HTTP; the send happens with no open SQL transaction. This only works if publication uses the same `knowledge-family:<uuid>` then `knowledge-document:<uuid>` lock names/order and relation-aware fresh eligibility. Existing citation membership is insufficient: adding an amendment can make the queued answer incomplete while the cited base still matches; cancelling a base can make it ineligible while the row and chunk still exist. The publication fence must coordinate with delivery, commit eligibility/relation changes atomically, and ensure a fresh queued answer is suppressed when family rule membership/eligibility changes. Add actual barrier evidence that publication waits for a paused delivery or delivery sees the committed new family state and suppresses, with no stale send window.

## Minimal additive implementation sequence

The sequence below preserves existing tables and completed prerequisites. Root should freeze each exact payload/status/lock contract before its own code changes.

1. **Freeze approval contract** — declare the relationship between the Task4 `COMPLETED` bullet and current `READY | FAILED` availability state. Preferred minimal shape is a private immutable publication receipt keyed uniquely by `job_id`, bound to job/extraction/review revisions, actor, exact review payload hash and plan digest, resulting document ID/storage mode, and creation time. Exact retry for the same binding returns the same result; another/stale binding conflicts. If the job itself must show completion, add an explicit publication field or extend its check additively and prove parsing/migration compatibility. Do not rewrite applied migrations or mutate encrypted review history.
2. **Complete immutable locations before approval** — verify `20261006044000_knowledge_source_locations.sql` and all-format citations/delivery equality acceptance is on the guarded local/DEVELOPMENT source. Approval rejects newly created chunks with empty/malformed/mixed-format locations or null/out-of-range token count; existing legacy rows stay `[]`/NULL. No auto-backfill.
3. **Add pure publication validation and located embedding preparation** — proposed `lib/imports/publication-contract.ts` (strict complete metadata, warning/privacy/action/target-mode checks) and `lib/knowledge/located-embedding-preparation.ts` (embed exactly the recomputed plan chunks in bounded batches with pinned local E5 identity). Optionally add fixed-registry mapper boundaries only after STR-01. No arbitrary SQL/table identifiers, requested vectors, caller-selected model or requests that supply source locations.
4. **Add preparation/finalization service** — proposed `lib/imports/import-publication.ts`: preflight active-admin; load and decrypt exact saved preview/review; enforce three counters and v2 explicit plan acknowledgment; recompute original/extraction-bound plan; map dataset rows with fixed installed mapper; obtain vectors outside SQL. Then start a short transaction, reauthorize, lock job `FOR UPDATE`, and in a fresh statement after the lock wait re-read job/extraction/review counters and current saved receipt. Acquire sorted family then sorted target/document advisory locks; recheck target and stream revisions, active role, scope, warning/privacy state and absence/presence of publication receipt; perform all version/relationship/chunk/(supported dataset)/activity/receipt effects atomically. Release locks in reverse order. Never carry the local E5 or other network work into the transaction.
5. **Add private API** — proposed `app/api/knowledge/imports/[id]/approve/route.ts` (or freeze one canonical route before coding), `lib/imports/import-api.ts` safe status mapping, same-origin/write body guard and fixed request schema containing only expected counters and the existing reviewed intent. No browser-supplied text, metadata, vectors, locations, SQL, provider, mapper or effect flags. Return private no-store document/receipt result; 401/403/404/409/422/503 responses do not expose originals, PII, ciphertext, SQL/provider output, or raw exception.
6. **Add meaningful tests** — pure review-bound action/privacy/plan checks; route strict body/auth/origin/status checks; real PostgreSQL integration for same-job concurrent retries (one publication/receipt), stale/revoked actor/target/review conflicts, each of all five actions plus whole CANCELS, family-wide occupied stream, missing metadata/warnings/sensitivity, forced insert/audit/receipt failure rollback, all five-format location/token/vector persistence, legacy row preservation and service-role/browser grants. Actual race test commits a newer review while approval waits on job lock and proves it does not use the old statement snapshot. A test seam must prove all embedding/mapper/network work completes with no open business SQL transaction.
7. **Prove retrieval, outbox and BOTH separately** — actual PG retrieval/citation tests for base+all active applicable amendments and cancellations at before/after dates; eligibility change invalidates stale evidence even when base chunk still exists. Real paused-outbox/family-lock barrier proves no stale AI send. Only after seven M8 schemas and per-dataset mappers exist, prove RAG+structured rows from the same reviewed version in the same approval transaction with all-or-nothing rollback, exact structured citations, and current/history filtering. STR-01/STR-02 remain an explicit prerequisite; no mode downgrade or partial BOTH success.
8. **Acceptance and evidence** — final-source full relevant unit/type/lint/build/replay/advisors, local PG/RLS and guarded DEVELOPMENT apply, actual authenticated browser/admin approval and Staff denial/conflict/retry, then update task board, requirements matrix, decision log for resolved mismatches, and dated component report. Do not mark M7/V1 complete; corpus approval, M8/M9, deployment and Flow A–F remain independent gates.

## Requirement discrepancies to carry into root freeze

- Master §41 names `academic_calendar_events`, `tuition_fees`, `transfer_courses`, `university_services`, `service_forms`, `announcements`; current design/types require seven and include `university_systems`. The seven-code contract is also an AGENTS invariant. Update documentation mapping/record the conflict when M8 implementation is planned.
- Master §42's bare “Admin must Approve” for an unknown schema leaves the target dataset behavior unclear. Original versioning §§8–10 allow RAG until a schema is deliberately built; current design says preserve the candidate and never auto-DDL. Keep that explicit distinction.
- The original versioning sample proposes a `document_versions` table and denormalized current/page fields on chunks; current schema uses `documents.revision`, `document_families`, `document_relationships`, and document-owned current/effective state. This is a physical-model mapping, not permission to skip user-visible history, citations, or all action behavior. `source_locations` on chunks is now the additive, proven provenance extension.
- Original versioning offers Replace/Add/History and discusses amendments informally. Master §§39–40 and DEC-025 define the current five review actions plus whole-document `CANCELS` as a relationship-bearing `ADD_ADDITIONAL`. Do not collapse it to the original three radio choices or treat cancellation as partial text editing.
- Task4's “set import job COMPLETED” must be reconciled with the present status constraint and current design statement that READY/FAILED represent availability. Preserve that distinction unless root records a decision and applies a compatible additive contract.
