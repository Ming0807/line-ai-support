# M4 LINE delivery and outbox independent review

## Spec verdict

The core delivery lifecycle matches the frozen M4 contract. Reply attempts are single-use: a prior attempt is `UNKNOWN`, timeout/408/5xx does not fall back to Push, and a known Reply 429 is terminal. An unused expired Reply switches to Push before the request. Push sends the persisted retry key on first attempt, treats 409 as accepted, retries retryable outcomes only within 24 hours, and does not read response bodies. These behaviors match the frozen plan and the already verified LINE references summarized in `m4-line-transport.md`.

The worker persists attempt count, first-attempt time, effective delivery mode, and the encrypted recipient snapshot before HTTP. Finalization and delivery-attempt insertion are transactional; accepted Push retry after finalization failure remains safe through the stable LINE key. Network I/O occurs with no open SQL transaction. Session advisory locks use the same conversation lock key as HUMAN ticket actions, and the dispatch/takeover integration test exercises this race. The worker uses `DIRECT_URL`, rejects the known transaction-pooler port/flag, and remote `databaseConnection` requires TLS verification. No retry, lease-fencing, HUMAN takeover, or pool-mode implementation blocker was found in these paths.

**Finding — P2: outbox accepts channel/kind mismatches — RESOLVED in the reviewed working tree.** `validateOutboxTarget` now enforces the matrix at both enqueue and dispatch (`lib/queue/outbox-target.ts`, called by `lib/queue/outbox.ts` and `lib/queue/run-outbox.ts`), and the M4 migration adds both target-shape and channel/kind `CHECK` constraints (`20261004081404_ticket_core_delivery.sql:48-53`). The focused `tests/outbox-input.test.ts` rejects both `STAFF/STAFF` and `STUDENT/NOTIFICATION` before any SQL. I inspected all current `enqueueOutbound` call sites: Student `SYSTEM` acknowledgements/responses and `STAFF` replies carry a session target; individual Staff notifications use `STAFF/NOTIFICATION`, a staff recipient, ticket, and PUSH. These fit the enforced shapes. The dispatcher revalidates the leased row before identity lookup, payload decryption, or HTTP. Parent reports a witnessed RED before the guard and GREEN afterward; I did not execute tests or touch the database. No current call-site compatibility problem found.

## Quality verdict

Transport validation is strict and bounded; it avoids logging or exposing credentials, message bodies, reply tokens, or raw response bodies. The payload remains encrypted, staff notifications are targeted individually, and Staff identity/scope is rechecked at dispatch. Existing tests cover LINE reply/push outcomes, timeout and retry-key stability, committed attempts before HTTP, Push finalization failure, exclusive ordered claims, expired Reply lease to `UNKNOWN`, and the bounded HTTP/takeover race.

Two focused coverage gaps remain in the source snapshot I reviewed; the parent reports both are being addressed by in-progress tests:

- There is no `runOutboxCycle` integration case in the reviewed snapshot that dispatches a Staff notification through the STAFF token to its bound LINE ID. The ticket-security fixture verifies recipient selection and encrypted notification content, but not the Staff sender path or its delivery-attempt/final status. The parent says an actual Staff sender PG case is being authored; until it lands and passes, this remains an evidence gap. It should assert the selected STAFF token, bound recipient, and final delivery state.
- The outbox-level test does not yet prove an expired, never-attempted Reply is persisted as `PUSH` before HTTP; only the transport unit test covers the switch, while the PG fixture covers an attempted Reply becoming `UNKNOWN`. The parent says a persisted-mode-before-fetch PG case is being authored. Confirm it lands and passes before treating this path as integration-verified.
- Staff binding changes are not serialized with the first-send preflight in M4. `run-outbox.ts:37-53` reads the active eligible mapping, then persists that mapping and calls LINE. Retries recheck and suppress when the mapping differs, but a concurrent binding/revocation write could race the first preflight. There is no binding writer in this scope. The parent plans for M9 to take the shared `delivery:STAFF:staffId` advisory lock in binding mutations; ensure it uses the same key and add a barrier race test when that writer is introduced. This is a future integration concern, not an M4 blocker.

Parent reports the broader current local gates passing. I did not run the database suite or remote checks for this re-review.

## Overall

The channel/kind spec gap is resolved at enqueue, dispatch, and database boundaries, and all current enqueue callers match those constraints. No active M4 delivery implementation blocker found in this review. The Staff sender and expired-unused-Reply persisted-mode integration cases are still evidence gaps in the reviewed snapshot; the parent reports those tests are in progress. The future Staff binding writer must share the dispatch advisory lock to close the first-send revocation race. No P0/P1 issue found. This was a source review only; I did not run PG or remote operations.
