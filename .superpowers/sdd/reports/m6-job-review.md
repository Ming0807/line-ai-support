Reviewed the durable job schema and functions, worker, dispatch evidence fence and outbox, Luna’s knowledge answer producer, the inbox integration and quick-reply lifecycle, the M6 plan, and current job/worker/producer tests. This was read-only; I did not run tests or access DEV, secrets, or provider APIs. The two producer grounding gaps below remain open pending the delegated fix and regressions. This review does not accept M6 or its production integration.

## Original findings (resolved afterward; see root verification below)

**P2 — The producer accepts classifier-invented applicability dimensions that were not stated by the user.** After parsing the classifier result, `createKnowledgeProducer()` validates only temporal scope ([answer-producer.ts:154-159](../../../lib/knowledge/answer-producer.ts)); `temporalScopeMatches()` does not compare audience, student type, program, curriculum, cohort, semester, or department with explicit question text. A model-invented population can therefore narrow retrieval to documents for that group and return a confident answer that does not apply to the student. Existing pure tests expect clarification for each unmentioned dimension ([knowledge-producer.test.ts:117](../../../tests/knowledge-producer.test.ts)), but the current implementation does not enforce those expectations.

Reproducer: for “What are the current transfer rules?”, have the scope classifier return `studentType='UNDERGRADUATE'` (or an unmentioned program/cohort); let search return an eligible chunk; the producer proceeds to answer rather than clarifying. Ground each applicability field in explicit user text, or clarify before embedding/search when a field is inferred.

**P2 — Direct references to a prior user-stated year can be treated as current scope.** The scope prompt allows history to resolve direct references, but `timeInQuestion()` extracts years/dates only from the current question and `temporalScopeMatches()` requires the temporal value to occur there ([answer-producer.ts:41-64](../../../lib/knowledge/answer-producer.ts)). After a user explicitly asks about year 2567, a follow-up such as “What about that year?” can be classified as current and pass the guard, sending current-policy retrieval for a historical reference. If the classifier does return historical scope, the guard rejects it and unnecessarily asks the user to restate the year. Only a direct temporal reference resolvable from trusted prior USER text should inherit a year/date; if it cannot be resolved confidently, clarify rather than silently searching current scope. Do not infer identity or applicability from assistant text.

Reproducer: history contains a user turn explicitly naming academic year 2567; the current question asks “What about that year?”; have the classifier return current scope and observe embedding/search proceed. Add coverage for the explicit user-history reference, unresolved reference, and assistant-only mention cases ([knowledge-producer.test.ts:134](../../../tests/knowledge-producer.test.ts)).

## Reviewed boundaries

The job table is private, RLS-enabled, denied to browser roles, and stores request/result payloads encrypted. Enqueue checks message ownership and AI/HUMAN eligibility under the conversation lock. Claim uses `SKIP LOCKED`, per-conversation ordering, database-clock leases, and a five-attempt ceiling; lease tokens fence result persistence, finalization, and retry. The committed snapshot precedes provider work, and a saved result lets retries finalize without another generation. Finalization rechecks ownership/mode/revision, validates citations against fresh retrieval while holding cited document row locks, and commits the AI message, outbox, and job status together. Logs omit message text, reply tokens, provider details, and generated result content.

The inbox path keeps AI opt-in disabled by default and only the worker enables it for the exact `YRU_AI_ENABLED=true` value ([student-processing.ts:12](../../../lib/conversation/student-processing.ts), [worker.ts:15](../../../scripts/worker.ts)). In AI mode, routed TEXT is prepared as an encrypted job in the inbox transaction without a system acknowledgment; HUMAN and unresolved context paths keep their existing routing behavior. Quick replies remain opaque server-stored choices bound to session, expiry, and the current candidate/revision snapshot ([quick-reply.ts:9](../../../lib/conversation/quick-reply.ts)). For final-answer choices, no old pending message ID is attached, so choosing NEW cannot move or regenerate the already-routed question; the handler asks the student to send a new message instead ([student-processing.ts:27](../../../lib/conversation/student-processing.ts)). The added actual-PG cases cover that behavior and verify a new-topic pending text is jobbed separately while HUMAN continuation creates no AI job ([student-ticket.integration.ts:333](../../../tests/database/student-ticket.integration.ts)). I found no concrete defect in this inbox/quick-reply change.

The dispatch evidence fence reloads the encrypted completed result, obtains sorted document session locks, re-runs retrieval in a short transaction, and holds locks through LINE dispatch. M7 publication writers must use the same document locks in sorted order. The answer producer bounds classifier, embedding, retrieval, and answer stages; validates retrieved evidence and model citations; and maps provider/search failures to fixed Thai clarifications. Root reports the worker is still not connected to production inbox processing, so this review is not a production-readiness or M6 acceptance decision.
