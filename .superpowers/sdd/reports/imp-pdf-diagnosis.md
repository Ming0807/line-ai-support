## Findings

The reported preview input is 105,655 bytes and has one page. Its `getInfo` and `getText` stages succeed; text extraction returns 1,093 characters with no replacement characters. Its `getTable` stage fails with a `TypeError` caused by an absent horizontal line. The same failure occurs in the exact bounded child and the production parser dispatch fails as `IMPORT_PARSER_FAILED`. The parser child does not leak its private exception or stderr to the request; that safe boundary also hides the useful distinction between this table-stage failure and malformed input.

The cause is in the installed table geometry implementation. `Table.findBottomLineIndex()` returns `-1` when no lower horizontal line spans a cell midpoint (`node_modules/pdf-parse/dist/pdf-parse/esm/geometry/Table.js:193-200`). `Table.getRow()` then indexes `hLines[-1]` and dereferences `bottomHLine.from.y` without checking the missing line (`:212-229`). On the reported preview, instrumentation observed 11 bottom-line lookups, one miss, and one row error. The line store had no rejected or zero-length lines, so a degenerate zero-length segment was not the trigger. `LineStore.getTableData()` calls `Table.toData()` directly and does not catch a malformed table (`node_modules/pdf-parse/dist/pdf-parse/esm/geometry/LineStore.js:23-29`).

A small geometry-only probe isolates this defect: a complete one-row, one-cell grid produces one row and one cell; shortening the lower horizontal boundary so it does not cross the second cell midpoint produces the same `TypeError` / `UNDEFINED_READ_FROM`. The generated minimal-PDF control and shortened-boundary variant both parsed without a missing-line event, so the geometry probe and the real-input reproduction are the proven reproductions; the generated PDF is not claimed as a reproducer.

The separate latest-analyze input is 1,891,757 bytes and has 28 pages. Its `getInfo`, `getText`, and `getTable` stages all succeed. The table stage returns 35 tables, 99 rows, and 122 cells. It also returns one table with zero rows and 22 rows with zero cells across pages 7, 8, 10–14, 16, 18–19, 22, 24–25, and 28. The maximum observed row width is 4 and maximum cell length is 152 characters; all values are within the configured table, row, column, cell, and character limits. The adapter rejects a zero-row table at `lib/imports/pdf-parser.ts:101` and a zero-cell row at `:106`, mapping either to `IMPORT_PARSE_INVALID`. These empty geometry results are sufficient to explain the adapter rejection; I did not instrument a post-filter build to prove there are no additional later validation failures.

The latest-analyze text stage returns 20,389 characters over all 28 pages with no replacement characters. Its table results have no bottom-line miss, rejected line, zero-length line, or row error. The bounded diagnostic child reproduces the parser-stage behavior; direct `parsePdfSource` and production `parseImportSource` separately reproduce the adapter failure. This is not explained by the child heap, timeout, or request byte/page limits. The direct adapter call fails in under half a second on the latest input; bounded child dispatch completes in about two seconds before returning the fixed failure. The current 256 MiB child heap and 15-second bound were not exhausted.

## Minimal adapter repair to evaluate

Keep the existing source bytes, physical pages, and all text. If `getTable()` throws after info/text succeeded, continue extraction with no table claims and add page-scoped `UNSUPPORTED_TABLES` blocking warnings plus page review evidence for every page, because the failing page cannot be identified safely from the failed aggregate. If `getTable()` succeeds but contains zero-row tables or zero-cell rows, skip only those unrepresentable empty shapes; retain every nonempty table row and exact cell string in order, and add page-scoped blocking `UNSUPPORTED_TABLES` and `TABLE_SHAPE_REVIEW` evidence for each affected page. Do not synthesize cells, infer missing row values, or clear review requirements. This retains valid tables on unaffected pages and all page text while making incomplete table structure explicit and blocking publication until review. No resource limit increase is indicated.

The preview result suggests a user-facing parser failure should distinguish bounded table extraction failure from invalid bytes if that response contract is changed. That response change is outside this diagnosis; the current production boundary continues to return only fixed error codes and does not expose raw exception text.
