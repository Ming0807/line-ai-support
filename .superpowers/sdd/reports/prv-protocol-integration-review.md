# PRV-02 protocol integration review

Date: 2026-10-04  
Reviewer: `/root/docs_provider_review`  
Scope: read-only review of the Chat Completions adapter and the current registry / fixed-endpoint Responses integration. No implementation files were edited.

## Findings

1. **[P2] Zen Responses parsing can return both a final answer and tool actions.** `parseResponse` accumulates output text and function calls independently, then rejects only multiple text parts or an empty result (`lib/ai/providers/openai.ts:274-317`). The gateway accepts a non-null output alongside tool calls (`lib/ai/gateway.ts:81-83`). A single upstream result can therefore reach the caller as both a structured answer and an executable backend tool request. The Chat Completions adapter rejects this mixed state (`lib/ai/providers/chat-completions.ts:335-349`), so Zen's two protocols have inconsistent safety behavior. Reject a completed Responses payload when it contains both output text and function calls, and add a fake-HTTP test asserting `INVALID_OUTPUT` with the actual 200 status. Also test oversized tool-call arrays and control characters in `call_id`; Responses currently checks call-ID length/uniqueness but does not enforce the Chat adapter's safe ID character set.

2. **[P2, limited to direct factory callers] Zen Responses health uses an unverified model-specific path.** `createZenResponsesAdapter` inherits the shared `GET /models/{modelId}` health check (`lib/ai/providers/openai.ts:324-368`). The current Zen docs document `GET /zen/v1/models` as the model catalog; their model table's model-specific paths identify inference endpoints, not a metadata GET contract ([Zen API documentation](https://opencode.ai/docs/en/zen/), catalog endpoint at lines 221-225). The production registry currently masks this path by wiring Zen health to the Chat adapter's `GET /models` check (`lib/ai/provider-registry.ts:19-25`), so the normal registry path does not appear to call inference. Keep the direct exported Zen adapter consistent with the verified catalog contract or make it unavailable as a standalone adapter; add tests that require exact model presence in the catalog, degrade on malformed/absent model data, and assert GET/no body/no POST.

## Reviewed controls

- **Zen protocol selection is explicit and conservative.** The price reader requires both the exact Zen model in Zen's `/models` catalog and a supported per-model Models.dev npm value (`@ai-sdk/openai` → `RESPONSES`, `@ai-sdk/openai-compatible` → `CHAT`); unsupported values remain `UNKNOWN` (`lib/ai/pricing.ts:92-101`). This matches the provider's documented per-model endpoint/package table and avoids suffix/name-based protocol guessing. `tests/ai-pricing.test.ts:37-45` covers per-model Responses metadata and an unavailable model. A useful integration test would carry these fake catalog results through `authorizeModelCost`/gateway into the matching registry protocol; the provider-registry tests currently hard-code `apiFormat` in the request fixture despite describing it as verified metadata.
- **Credential host separation is enforced at the registry boundary.** `pinned` binds each registry entry to its own official root (`lib/ai/provider-registry.ts:8-25`), and `tests/provider-registry.test.ts:44-50` asserts swapped Zen/OpenRouter credentials are rejected before fetch. The price reader is separately documented as public and keyless (`lib/ai/pricing.ts:43-45`). One small edge to settle: `pinned` accepts a trailing slash while the Chat adapter's `providerFor` accepts only the slashless canonical base; current behavior remains fail-closed but inconsistent.
- **Actual HTTP status survives invalid HTTP 200 payloads.** Responses parsing wraps body/output failures with `response.status` (`lib/ai/providers/openai.ts:343-347`), covered by `tests/provider-registry.test.ts:40-42`; Chat does the same (`lib/ai/providers/chat-completions.ts:379-396`), with a 200 oversized-body case in `tests/chat-completions.test.ts:254-260`.
- **No paid inference is hidden in the registry health path.** Zen registry health delegates to the metadata GET path; Chat health uses GET `/models` for Zen and validates the model ID in the returned catalog (`lib/ai/provider-registry.ts:24`, `lib/ai/providers/chat-completions.ts:354-362,400-426`). Tests currently cover OpenRouter Chat metadata health, but do not assert Zen registry health's GET/no-body/no-inference contract. Add that regression test; also verify the metadata result is never represented as generation success.
