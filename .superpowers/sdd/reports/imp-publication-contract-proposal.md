# IMP-03 strict review and publication contract proposal

Reviewed 6 October 2026 for the current staged extraction and preview implementation. This is a read-only contract proposal for root integration; it is not implementation or acceptance evidence and does not approve any YRU corpus item.

## Existing schema and fences to reuse

Use one `public.documents` row per retained version. The existing columns already cover the publication decision: `document_family_id`, `department_id`, `title`, `document_type`, `version_name`, `version_stream`, `academic_year`, `semester`, `audience`, `student_type`, `program_code`, `curriculum_code`, `cohort`, `published_at`, `effective_from`, `effective_to`, `status`, `is_current`, `authority_level`, `approval_status`, `approved_by`, `approved_at`, `official_source`, `extraction_reviewed`, `requires_review`, `visibility`, `archive_only`, `source_url`, `source_page_url`, `mime_type`, `checksum`, `supersedes_document_id`, and `revision`. Reuse `document_families(code,name,category,default_storage_mode)`, `document_relationships(source_document_id,target_document_id,relation_type)`, and `knowledge_chunks(document_id,chunk_index,page_number,section_title,content,embedding_e5,embedding_dimensions,embedding_fingerprint,requires_review)`. Keep every old document and its chunks; a replacement updates the old row's eligibility and inserts a new version. `document_versions` is optional in the old master and is unnecessary with this existing shape.

The partial unique index `documents_one_current_stream_idx(document_family_id,version_stream) WHERE is_current` is the final database guard for current uniqueness. `documents.revision` is already embedded in retrieved `KnowledgeEvidence` and citations, so increment it when a row's content or eligibility changes. For `REPLACE_CURRENT`, use the existing `supersedes_document_id` and insert `document_relationships` with the new document as source and the replaced document as target.

Do not overload `private.knowledge_import_jobs.status`: its current `READY|FAILED` state is extraction availability, and its original-source trigger protects immutable bytes/checksum/provenance. It has no publication result field today. Add a private immutable publication receipt keyed uniquely by `job_id` (with job/extraction revision, actor, resulting document id/revision, canonical request hash, and commit time) so duplicate approval returns the same document while a changed request conflicts. Keep review data out of `private.activities` except for safe codes and IDs.

The delivery worker takes `delivery:<channel>:<lane>`, then family/document session advisory locks while it revalidates cited knowledge and sends LINE HTTP (bounded to 5 seconds). Reuse the exact `knowledge-family:<uuid>` then `knowledge-document:<uuid>` keys exported by `lib/knowledge/delivery-fence.ts`; acquire affected family IDs sorted, then document IDs sorted, before row locks. Publication should wait on these common keys with a bounded lock timeout. Do not acquire recipient lane locks: the affected student lanes cannot be enumerated. A publisher that does not need the lane lock avoids a lane→family/family→lane cycle. Embedding, parser, Storage and other network calls must finish before this short transaction.

## Review draft and final approval DTOs

Keep review-draft saving separate from publication. Add an append-only private review receipt/revision bound to both `job_revision` and `extraction_revision`; store the reviewed payload encrypted with the existing staging envelope and `purpose:'REVIEW'`. Suggested columns: `job_id`, `review_revision`, `job_revision`, `extraction_revision`, `actor_id`, `payload_hash`, `review_encrypted`, `created_at`; primary key `(job_id,review_revision)` and FK `(job_id,extraction_revision)` to `private.knowledge_import_revisions`. Give the server role `SELECT, INSERT`, deny browser roles, and reject update/delete. Saving a review draft creates no `documents`, chunks, relationship, or publication status change.

The strict draft payload should contain only explicit reviewer choices:

```ts
{
  expectedJobRevision: number,
  expectedExtractionRevision: number,
  expectedReviewRevision: number, // 0 for first save
  metadata: {
    title, familyCode, newFamily: null | { name, category },
    departmentCode, documentType, versionName, versionStream,
    academicYear, semester, audience, studentType, programCode,
    curriculumCode, cohort, publishedAt, effectiveFrom, effectiveTo,
    authorityLevel, sourceUrl, sourcePageUrl, visibility,
    storageMode: 'RAG'
  },
  action: 'NEW_FAMILY' | 'ADD_ADDITIONAL' | 'REPLACE_CURRENT' |
          'ADD_HISTORICAL' | 'AMEND_EXISTING',
  target: null | { documentId: UUID, documentRevision: number },
  relationship: null | {
    type: 'CANCELS', targetDocumentId: UUID, targetRevision: number
  },
  attestations: {
    sourceAuthorityReviewed: true,
    extractionComparedWithSource: true,
    applicabilityReviewed: true,
    sensitivityReviewed: true
  },
  warningDispositions: [{ warningKey, disposition, reason }]
}
```

All fields are strict and server-validated. The API computes warning keys from the exact immutable extraction report; callers cannot invent keys, omit unresolved warnings to clear them, or supply parser/analysis results. `sourceUrl` must be a separately reviewed official YRU URL with preserved acquisition provenance; `fetchedAt` is never copied to `publishedAt` or effective dates. Dates use actual calendar validation, and `effectiveFrom` is required before setting any row `ACTIVE`. Authority and scope are human-reviewed; an analyzer suggestion is never approval. `official_source`, `extraction_reviewed`, `requires_review`, `approved_by`, and `approved_at` are set by the publication service from validated evidence, never copied from a request boolean. `storageMode` is a review guard in this M7 DTO, not an existing per-document column; persist no invented dataset/table field and accept only RAG until M8 installs the fixed registry.

`expectedJobRevision` must match the current import-job pointer and `expectedExtractionRevision` must match the extraction actually displayed/reviewed. The independent review revision prevents parallel draft writes. Approval consumes the saved review receipt and repeats all checks after locks, including active-SUPER_ADMIN authorization, job status/revision/checksum, target revision/current status, family/stream/action compatibility, and warning gates. If extraction advances after review, the review receipt remains as history but cannot publish. Do not publish a prior extraction while the job's latest receipt is `FAILED`; require a successful analysis or an explicit recovery path.

The five master action names remain unchanged. `CANCELS` is a relationship on an `ADD_ADDITIONAL` cancellation instrument, with its own exact `targetDocumentId` and `targetRevision`; this keeps the action vocabulary and models cancellation as a separately approved source. The 19 initial family codes are seed/coverage expectations, not an allowlist: an explicitly reviewed new family is allowed as a `document_families` data row, under a code-scoped advisory lock and unique-code check. It never creates a table or migration.

## Version, relationship, warning, and visibility rules

- **Stream identity:** `version_stream` represents a stable series/scope, not the version name, academic year, or effective date. `REPLACE_CURRENT` must copy the selected current row's stream and match its family, document type, department, audience, student type, semester, program, curriculum, and cohort exactly. A reviewer cannot point a new version at a merely similar document. For a new/additional series, the server derives or validates a distinct stream from the reviewed scope; collisions are conflicts, not permission to supersede an unrelated row.
- **`NEW_FAMILY`:** target and relationship are null. Create a family row and first approved document in the same transaction. Recheck the family code under a stable code-scoped lock; on conflict, return a stale-review conflict.
- **`ADD_ADDITIONAL`:** no target and no relation means an independent approved document in a distinct stream; no existing current row is changed. With `relationship.type='CANCELS'`, create a separately reviewed cancellation instrument tied to one exact target/revision. Scope must match the target; partial/provision-level cancellation is unsupported and remains unpublished for manual resolution.
- **`REPLACE_CURRENT`:** exact target/revision required. Target must still be the approved current row in the same stream/scope. In one transaction set old `status='SUPERSEDED'`, `is_current=false`, increment its revision, insert new `status='ACTIVE'`, `is_current=true`, set `supersedes_document_id`, add `SUPERSEDES`, chunks, receipt and audit. Never delete old rows/chunks.
- **`ADD_HISTORICAL`:** no current row is changed. Insert `is_current=false`, with reviewed version/year/effective facts and `status='SUPERSEDED'` when it is a known older version; this status is included by the existing explicit historical retrieval path. Do not set `archive_only=true` for a source meant to answer historical questions: current retrieval excludes archive-only records, and historical SQL currently excludes `ARCHIVED`/archive-only rows. Adding a known supersedes edge requires an explicitly selected newer source and its revision; do not infer direction from the upload order.
- **`AMEND_EXISTING`:** exact base target/revision required; target must be a base document, not an amendment. Insert a separately approved, effective amendment and `AMENDS` edge from the new amendment source to the base target. Leave the base's status/current flag unchanged. V1 does not auto-resolve amendment chains or provision-level effects.
- **`CANCELS`:** relation source is the new, approved cancellation instrument; target is the exact document/revision it cancels. It excludes that document only while the cancellation source is applicable at the current/as-of date. Cancelling an amendment leaves base/other amendments eligible; cancelling a base excludes the entire base-plus-amendments group. Never flip the target's current flag/status: historical queries before the cancellation date must still return the formerly applicable rule. Whether a finite `effectiveTo` temporarily restores a cancelled rule is a domain policy to lock before implementation; safest initial interpretation is interval-based eligibility, and a permanent cancellation has no end date.
- **Warning dispositions:** immutable `ExtractionReport` warnings stay `UNRESOLVED`; the reviewer receipt adds actor, exact warning key, disposition, reason, job/extraction revision. No disposition erases original evidence. `CORRECTED` must be tied to a later edited/reanalyzed extraction revision. `FALSE_POSITIVE` may be accepted only for a non-sensitive, non-blocking review warning with a reason; it cannot clear any sensitive category, `SENSITIVE_DATA_REVIEW_REQUIRED`, `SOURCE_REVIEW_REQUIRED`, or blocking parser/provenance warning. Missing disposition means unresolved. For `PUBLIC`, require reviewed official provenance, no current sensitive categories after reanalysis, no unresolved blocking/provenance/quality warnings, and all other warnings resolved by evidence. Redaction creates a new staged extraction revision while the private original/checksum remains unchanged. Acknowledging a detector result never authorizes unredacted personal data in public RAG.
- **Visibility:** unresolved sensitive data may remain only in private staging. `INTERNAL`/`RESTRICTED` does not itself authorize exposure: current retrieval is public-only and no staff knowledge retrieval permission path was accepted in this scope. Do not publish flagged personal content until a separately tested staff-scope retrieval/read contract exists. `STRUCTURED` and `BOTH` are also unpublishable in this M7 slice; the seven fixed mappers belong to M8. Preserve such proposals for review, default publication to RAG, and perform no dynamic SQL/DDL.

## Retrieval and delivery acceptance risks

The current `lib/knowledge/retrieval.ts` filters approved, official, reviewed, non-review, public, non-archive documents by status/current/effective/scope before vector similarity. Its evidence/citation fields include `documentRevision`, page, section and source URL. Current `knowledge_chunks` and `KnowledgeEvidence` do not store/carry the discriminated PDF/DOCX/XLSX/CSV/HTML `SourceLocation`; the current chunker drops most format locations. Add a persisted per-chunk location and carry it unchanged through retrieval and citations before claiming source-location acceptance: never fabricate DOCX/HTML pages; preserve PDF page/block/table, DOCX block/heading/table, XLSX sheet/row/column/table, CSV record/column/table, and HTML final URL/block/heading/table. Verify parser→chunk→citation equality for all five formats.

The current `verifyAIOutboxEvidence` takes the correct family/document locks but validates only that each cited item remains somewhere in fresh retrieval. If an `AMENDS` publication leaves the cited base chunk unchanged, an old queued answer citing only the base can still pass after the amendment changes the applicable rule. Before publication acceptance, add a regression that pauses an old AI result, publishes an amendment, and proves the obsolete answer is suppressed. Either compare the complete previously retrieved evidence snapshot with the fresh result, including additions/removals/order-relevant metadata, or maintain and compare an affected rule-group revision. Merely incrementing the amendment row is insufficient when the old answer cites only the base; relationship publication must invalidate the base/group evidence revision too. Apply the same reasoning to `CANCELS` and new higher-authority overlapping versions.

The installed `EMBEDDING_SERVICE_DESIGN.md` supersedes provider-embedding examples in the old master approval section: chunking and passage embedding use the local E5 service selected by the human, CPU/384 normalized vectors, outside SQL. Validate exact model/revision/fingerprint/dimension and token/input bounds; do not call generation AI or choose a provider/cost/dataset. An embedding failure happens before publication begins.

## Atomic publication sequence and focused tests

1. Load the latest authorized preview/review; validate DTO and warning keys; chunk while carrying locations; prepare local E5 passage vectors outside SQL. Reject unknown/uninstalled structured schema, missing official PUBLIC provenance, sensitive categories, stale extraction, and unsupported relation/action combinations before publication.
2. Open a short transaction with bounded statement/lock timeouts; reauthorize active `SUPER_ADMIN`; lock the import job row and compare `READY`, current job revision, checksum, extraction revision and saved review receipt.
3. Acquire sorted existing family locks, then sorted exact target/base/cancellation document locks. Lock rows and revalidate exact target revision, scope, action, version stream, cancellation applicability and current uniqueness. Resolve family creation by code lock. A stale target/review or lock timeout makes no changes.
4. Atomically write document/family changes, relation(s), all chunks/vectors/location records, immutable publication receipt, and safe `private.activities` entries. Commit once. A duplicate same-job/same-review/request hash returns the stored document receipt; changed payload or second publication conflicts.

Required PostgreSQL acceptance: two concurrent replacements against one current target yield one winner; stale job/target/review revisions yield no write; duplicate same approval returns one document and chunk set; changed-body retry conflicts; trigger-failed chunk/relation/activity/receipt insertion rolls back old current changes and every new row; current unique index remains intact; active-role revocation before commit denies publication; embedding mock asserts no SQL transaction is open during HTTP; and a barrier proves publication waits for the in-flight LINE family/document fence. Retrieval cases cover current vs historical replacement, independent additional stream, `ADD_HISTORICAL`, two applicable amendments, expired/future/out-of-scope amendment, target-not-base rejection, `CANCELS` amendment vs base, as-of before/after cancellation and unchanged target current flags. Sensitivity cases prove false-positive acknowledgement never clears detected personal data, redaction is a new extraction revision, source/date/authority proposals remain untrusted, and no dynamic SQL or per-import migration occurs.

## Smallest coherent vertical slice and ownership

Root owns every contract, migration, authorization, database transaction, lock, API, retrieval and acceptance file. First implement only the save-review-draft slice: additive private immutable receipt migration; `lib/imports/review-service.ts`; one same-origin review-draft route; and `tests/database/import-review.integration.ts` plus route/pure DTO tests. It saves human metadata, exact warning dispositions and action/target revisions against `extractionRevision`, returns the immutable review receipt, and creates no public rows. The preview UI can consume this saved draft without implying approval. Then, under the same root ownership, add `lib/imports/version-resolver.ts`, `lib/imports/publish-service.ts`, `app/api/knowledge/approve/route.ts`, publication receipt migration, retrieval/citation location support, actual publication/retrieval DB tests and the stale-amendment delivery regression. Keep the first publishable mode RAG only; no reviewed corpus item is needed for controlled fixture acceptance.
